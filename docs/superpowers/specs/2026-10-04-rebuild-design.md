# 楽天ポイント計算ツール 作り直し設計

- 日付: 2026-10-04
- ブランチ: `rebuild/from-scratch`
- 用語: [用語集](../../glossary.md) に従う。この文書の用語は用語集の定義で読む。

## 目的

楽天のお買い物マラソンなどで獲得できるポイントを計算するツールを、作り直す。機能は旧サイトとほぼ同じにし、技術基盤とドメインモデルを一新する。旧サイトの設計は参考にしない。

旧サイトでは、次の問題が設計の構造に起因して解決できなかった。

| # | 旧サイトの問題 | この設計が満たす要件 |
|---|---|---|
| R1 | 再レンダリングが細かくない。atomFamily を使いこなせていない | 状態を正規化し、注文、商品、特典ごとの atom に分ける。1行を編集したとき、その行と影響する集計だけを再描画する |
| R2 | 機能をどこに足せばよいかわからず、ラクマへの対応などの仕様変更に追従できない | 特典の種類と購入先を拡張点にし、どこに足すかを構造で決める |
| R3 | 計算が正しいと言えない | 計算エンジンを React と Jotai から切り離した純粋関数にし、楽天の規則に沿った単体テストで正しさを担保する |
| R4 | 商品ごとの内訳を出せない | 計算結果を「商品 × 特典」ごとのポイントで返す。上限で削った分も按分する |
| R5 | 保存データを移行できず、更新のたびにデータが消える | 保存データのスキーマバージョンを管理し、マイグレーションを順に適用して Valibot で検証する |
| R6 | 複数のイベントを記録して見返せない | プランを最上位の単位にし、購入記録をプランごとに保存する |
| R7 | どのキャンペーンがどの回のものかを覚えておけない | 特典をプランに紐づけて保存する |
| R8 | キャンペーンの更新を開発者が保守し続ける必要がある | 特典をデータにし、ユーザーが複製、編集、新規作成できるようにする |
| R9 | Safari でデータが消える | 今回は対策しない。消えてもよいものとして扱い、将来の D1 保存で解決する |

## 範囲

### 含めるもの

- プラン、注文、商品の入力と、ポイントの計算、内訳の表示
- SPU の設定（プロフィール）とショップ台帳
- 公式イベント（マスタデータ）からのプラン作成と、特典の編集
- 商品 URL からの商品情報の取得
- ビルド時に生成する広告、Google Analytics、AdSense、共有ボタン
- 問い合わせフォーム、利用規約、お知らせ
- 購入先は楽天市場、楽天ブックス、ラクマ

### 含めないもの

- 楽天アカウントでのログインと、D1 への保存（将来の別の仕様で扱う）
- Safari でのデータ消失への対策（PWA 化、永続化の要求、書き出しと読み込み）
- 旧サイトの保存データの移行（旧データの形式は新しいモデルと対応しないため）
- 公式イベントごとの静的な解説ページ
- 上記3つ以外の購入先

## 1. 全体構成

### 配信

配信先は Cloudflare Workers の1つだけにする。TanStack Start の `prerender` で全ページをビルド時に HTML にし、静的アセットとして返す。このため、ページを表示するだけでは Worker の処理は動かない。Worker の処理が動くのは問い合わせのサーバー関数だけであり、将来のログインと D1 保存も同じ Worker に追加する。

楽天 API を呼ぶ場面は、ビルド時の広告の取得と、ブラウザからの商品情報の取得の2つである。

SPU のサービスアイコンとキャンペーン画像は楽天の画像なので、リポジトリには入れない。R2 のバケット `bmth-assets` の `point-sprint/img/` に置き、カスタムドメイン `https://assets.bmth.dev` から配信する。マスタデータの `imagePath` は `/img/...` のままにし、画面で表示するときに配信元の URL を前に付ける。

### パッケージ

pnpm workspaces で次の3つに分ける。

- `apps/web`: TanStack Start のアプリ。画面（`routes/`）、Jotai の atom（`state/`）、リポジトリの IndexedDB 実装（`storage/`）、問い合わせのサーバー関数（`server/`）を置く。
- `packages/ui`（`@workspaces/ui`）: Yamada UI のテーマと共通部品。アプリは Yamada UI を直接読み込まず、このパッケージを通して使う。
- `packages/domain`（`@workspaces/domain`）: React に依存しない部分。型と Valibot のスキーマ（`model/`）、特典の種類（`benefit-kinds/`）、購入先（`channels/`）、計算エンジン（`calculate/`）、マイグレーション（`migrations/`）、マスタデータ（`master/`）を置く。

依存の向きは `web → ui`、`web → domain` だけにする。`ui` と `domain` は互いに依存しない。`domain` は React、Jotai、ブラウザ API に依存せず、この制約は `packages/domain` の依存関係に React などを含めないことで強制する。

### ツール

oxlint、oxfmt、TypeScript、cspell、Vitest、Playwright を使う。CI は GitHub Actions で実行し、main へのマージ時にデプロイする。

## 2. ドメインモデル

`packages/domain/model` に Valibot のスキーマとして定義し、TypeScript の型はスキーマから導出する。

```ts
Profile    { spuBenefits: Benefit[], multiAccount?, accounts?: Account[] }
Account    { id, name }
Shop       { id, channel: ChannelId, shopCode?, name, tags: ShopTag[] }
Plan       { id, name, officialEventId?, accountId?, period: { start, end },
             benefits: Benefit[],
             orders: Order[] }
Order      { id, shopId, date, onHold, tags: OrderTag[], lineItems: LineItem[] }
LineItem   { id, name, unitPrice, quantity, taxRate, discount,
             shopPointRate?, itemCode?, url? }
Benefit    { id, kind: BenefitKindId, category: "base" | "spu" | "campaign",
             label, enabled, params, conditions,
             amountBasis: "tax-excluded" | "tax-included",
             capScope: "plan" | "campaign" | "month" | "day",
             sharedKey?, exclusiveGroup?, requires? }
Conditions { channels?, shopIds?, shopTags?, orderTags?, dateRule?, minOrderAmount? }
DateRule   { type: "daysOfMonth", days } | { type: "range", start, end }
           | { type: "dates", dates }
CampaignTemplate { id, name, benefit: Benefit, occurrence: "fixed" | "user-dates" | "user-period" }
OrderTag   "repeat"
```

- プランを作るとき、プロフィールの SPU と、参照した公式イベントの特典を `Plan.benefits` に複製する。複製後に元を変更しても、作成済みのプランは変わらない。
- `Benefit.params` は特典の種類ごとに形が異なり、その種類のスキーマで検証する。`Benefit.conditions` は種類によらず共通の適用条件である。
- `LineItem.unitPrice` は税込の単価、`taxRate` は 0.1、0.08、0（非課税）のいずれか、`discount` はその商品に適用したクーポンの値引額（税込、既定は 0）である。注文全体に効くクーポンは、ユーザーが商品に割り振って入力する。
- ショップ独自の倍率は特典ではなく `LineItem.shopPointRate` に持つ。値は商品検索 API の `pointRate` から入り、内訳には「ショップ倍率」の行として出す。
- `Benefit.amountBasis` は、ポイントの対象額を税抜の対象額にするか税込の対象額にするかを決める（既定は `"tax-excluded"`）。楽天カード通常分（カード本体の還元）だけが `"tax-included"` である。
- `Benefit.capScope` と `sharedKey` は上限の共有範囲を決める（3節「上限の共有範囲」）。
- `Account` は計算用の楽天アカウントで、利用者が見分けるための名前だけを持つ。認証情報は扱わない。`Plan.accountId` はそのプランで購入するアカウントで、省いたときは既定のアカウント（固定の ID `DEFAULT_ACCOUNT_ID`、名前「メイン」）とする。アカウントを導入する前に保存したプランも既定のアカウントのものになるので、マイグレーションは要らない。
- `Profile.accounts` は既定のアカウントを含むすべてのアカウントで、省いたときは既定のアカウント1件とする。既定のアカウントは名前を変えられるが、削除できない。`Profile.multiAccount` が `true` のときだけ、プランごとのアカウントを計算に使い、画面にアカウントの選択欄を出す。それまでは、すべてのプランを既定のアカウントのものとして計算する。削除したアカウントを指すプランも、既定のアカウントのものとして計算する。
- `Benefit.exclusiveGroup` が同じ特典は、同時に1つしか有効にできない（楽天カードと楽天プレミアムカードの特典分など）。1つを有効にすると、同じグループのほかの特典は無効になる。この切り替えは `toggleBenefit(plan, benefitId)` が行う。
- `Benefit.requires` は、その特典が前提にする特典の ID である。楽天カード特典分と楽天プレミアムカードの特典分は、楽天カードで払ったときに付くので、楽天カード通常分を前提にする。前提の特典は、前提にする特典のどれかが有効なときだけ有効にする。前提にする特典を有効にすると前提の特典も有効になり、最後の1つを無効にすると前提の特典も無効になる。前提の特典を有効にしたときに前提にする特典がどれも無効なら、並びの最初の1つ（楽天カード特典分）を有効にする。前提の特典を無効にすると、前提にする特典もすべて無効になる。この切り替えも `toggleBenefit` が行い、旧サイトの連動と同じ結果になる。
- `Shop.tags` はショップの属性で、最初のリリースでは `"39shop"`（送料無料ラインを 3,980円以下に設定しているショップ）だけを持つ。`Conditions.shopTags` を指定した特典は、そのすべての属性を持つショップの注文だけを対象にする。
- `Order.onHold`（保留）が `true` の注文は、計算から外す。買い回りのショップ数にも、合計にも、上限にも入れない。画面では、含めた場合のポイントを取り消し線で参考に出す（3節の `heldEstimates`）。
- `Order.tags` は注文の属性で、最初のリリースでは `"repeat"`（以前に買った商品を同じショップでもう一度買う、リピート購入）だけを持つ。`Conditions.orderTags` を指定した特典は、その属性をすべて持つ注文だけを対象にする。
- `Plan.orders` の並びは画面での並びであり、計算結果には影響しない。注文は並べ替えとコピーができる。コピーは、ID をすべて新しくした同じ内容の注文を、元の注文の直後に入れる。
- `Benefit.category` は、内訳の4区分（通常、SPU、マラソン、キャンペーン）を決める。`base` は通常（通常ポイントと楽天カード通常分）、`spu` は SPU、`shop-around` の種類の特典はマラソン、それ以外の `campaign` とショップ倍率はキャンペーンに数える。
- 定例キャンペーン（5と0のつく日、勝ったら倍、39ショップ、リピート購入）は `CampaignTemplate` としてマスタデータに持つ。`occurrence` が `"fixed"` のもの（5と0のつく日）は日付の規則で自動的に判定し、ユーザーはエントリーの有無を ON/OFF で切り替える。`"user-dates"` のもの（勝ったら倍）はユーザーがエントリーした日と倍率を、`"user-period"` のもの（39ショップ、リピート購入）はユーザーが開催期間と上限を入力し、テンプレートから特典を作ってプランに加える。
- マスタデータの更新が止まっても計算を続けられるように、お買い物マラソン・スーパーSALE の買いまわり（`shop-around`）と、倍率と上限を自由に決める特典（`rate-bonus`）もテンプレートとして持つ。利用者は公式イベントのプリセットからプランを作ることも、プリセットなしでプランを作ってこれらのテンプレートから自分で特典を足すこともできる。特典の倍率・上限・期間は、プリセットから作ったものも含めて、すべて利用者が上書きできる。
- ID は文字列（UUID）とする。

### 拡張点

特典の種類（`domain/benefit-kinds`）は、1つの種類が `params` のスキーマ、既定値、計算関数をまとめて持つ。最初のリリースでは次の2種類を作る。

- `rate-bonus`: 上限付きの倍率加算。SPU の各項目、0と5のつく日、39ショップなどを表す。`params` は `{ rate, cap?, roundingUnit: "item" | "order" }` である。
- `shop-around`: 買いまわり。ショップ数に応じて段階的に倍率を決める。`params` は `{ tiers: { minShops, rate }[], cap?, roundingUnit }` である。

特典の種類を追加するときは、`domain/benefit-kinds` に計算を、`apps/web` にその種類の `params` を編集する UI を追加する。編集 UI をスキーマから自動生成すれば追加先を1か所にできるが、その生成の仕組みのほうが大きくなるため採らない。

購入先（`domain/channels`）は、1つの購入先が `countsTowardShopAround`（買いまわりのショップ数に数えるか）、`receivesShopAround`（その購入先の注文に買いまわりの倍率が乗るか）、URL の解析方法、商品情報の取得に対応するかを持つ。最初のリリースでは次の3つを作る。

| 購入先 | ショップの単位 | ショップ数に数える | 買いまわりの倍率が乗る | 商品情報の取得 |
|---|---|---|---|---|
| 楽天市場 | 店舗ごと（ショップコード） | 数える | 乗る | 対応 |
| 楽天ブックス | 購入先全体で1ショップ | 数える | 乗る | 非対応 |
| ラクマ | 購入先全体で1ショップ | 数える | 乗らない | 非対応 |

「購入先全体で1ショップ」の購入先は、ショップ台帳にその購入先のショップを1件だけ置き、すべての注文をそのショップに紐づける。

### 保存の単位

IndexedDB には、プランごと、プロフィール、ショップごとに1レコードを保存する。各レコードは `updatedAt`（最終更新日時）を持つ。`updatedAt` は今の設計では使わないが、将来 D1 との同期を選んだときに競合の判定に必要になり、あとから足すとマイグレーションが要るため、最初から持たせる。

スキーマバージョンはレコードごとではなく、IndexedDB のデータベース全体で1つだけ持つ（4節）。

## 3. 計算エンジン

`packages/domain/calculate` に置く純粋関数である。

```ts
calculateAll(plans, shops) → Map<PlanId, CalculationResult>
calculate(plan, shops) → CalculationResult   // calculateAll([plan], shops) の1件
CalculationResult = {   // 下の項目に加えて heldEstimates: { orderId, points }[] と shopAroundOutlook を返す
  breakdown: { lineItemId, source: BenefitId | "shop-rate", points }[],
  benefitTotals: { benefitId, rawPoints, cappedPoints, capReached }[],
  shopCount, total, warnings
}
```

### 計算が従う楽天の規則

次の規則は楽天の公式の案内で確認した（2026-10-04 時点）。計算エンジンのテストは、これらの規則と案内の計算例から作る。

- 税抜額は商品ごとに求める。消費税額を「税込額 × 税率 ÷ (1 + 税率)」の小数点以下切り捨てで求め、税込額から引く。例: 税込 1,980円、税率 10% → 消費税額 180円 → 税抜 1,800円。（[楽天市場 FAQ: ポイント付与対象金額](https://ichiba.faq.rakuten.net/detail/000030997)）
- ポイントの対象額はクーポン適用後の金額である。送料とラッピング料は含めない。（同上）
- 通常のポイントは、商品ごとに「税抜額 × 1%」を小数点以下切り捨てで求め、合計する。例: 税抜 500円 × 6個 = 3,000円 → 30ポイント。倍率 +0.5 なら 200円につき 1ポイントになる。（[楽天市場 FAQ: 注文のポイント計算方法](https://ichiba.faq.rakuten.net/detail/000006644)）
- 楽天カードの還元は2つに分かれる。楽天カード通常分（カード本体の還元、1倍）は1注文ごとの決済額を**税込**（送料・ラッピング料を含む）で対象にし、上限はない。楽天カード特典分（SPU、+1倍）は1注文ごとの決済額を**税抜**（送料・ラッピング料を除く）で対象にし、月間の上限（楽天プレミアムカードなどは 5,000ポイント、その他は 1,000ポイント）がある。（[SPU](https://event.rakuten.co.jp/campaign/point-up/everyday/point/)）送料は入力しないので、通常分は送料の分だけ少なく計算される。
- SPU の一部（楽天カードの決済分）は1注文ごとの税抜額を対象にし、ほかの多くは1商品ごとの税抜額を対象にする。（[楽天市場 FAQ: SPU の注意点](https://ichiba-smp.faq.rakuten.net/detail/000031092)）
- 買いまわりのショップ数は、ショップごとに期間中の税込額（クーポン適用後、送料除く）を累計し、1,000円以上のショップを1と数える。同じショップで何回買っても1ショップである。倍率は全ショップを数え終えた結果で決まり、購入の順番によらない。上限はボーナス分だけにかかる。（[お買い物マラソン ガイド](https://event.rakuten.co.jp/campaign/point-up/marathon/guide/)）
- 楽天ブックスは買いまわりのショップ数に数え、買いまわりの倍率も乗る。（同上）
- ラクマは期間中の累計が1,000円以上なら買いまわりの1ショップに数えるが、ラクマでの購入には楽天市場の買いまわりの倍率は乗らない。（[ラクマ 買いまわり特典](https://rakuma.rakuten.co.jp/info/campaign/buy/kaimawari/)）

- 定例キャンペーンの上限の単位は次のとおり。5と0のつく日は月間合計で 1,000ポイント（[5と0のつく日](https://event.rakuten.co.jp/campaign/card/pointday/)）、勝ったら倍は開催ごと（勝利の翌日ごと）に 1,000ポイントで1注文 1,000円（税込）以上が条件（[勝ったら倍](https://event.rakuten.co.jp/campaign/sports/)）、39ショップは開催期間ごとに 3,000ポイントで1注文 3,980円（税込）以上が条件（[39ショップ](https://event.rakuten.co.jp/guide/freeshippingline/campaign/)）、お買い物マラソンは開催ごとに上限がある。SPU の上限は月間である。

### 上限の共有範囲

上限には、プランの中で閉じるものと、プランをまたいで共有するものがある。特典の `capScope` で範囲を決め、範囲が同じ特典の生のポイントを合計してから上限をかける。

| `capScope` | 上限をかける単位（グループのキー） | 例 |
|---|---|---|
| `plan` | プランごと、特典ごと（プラン ID と特典 ID） | ユーザーが自分で作った特典 |
| `campaign` | 同じアカウントのプランをまたいで1つ（アカウントと `sharedKey`） | お買い物マラソン、39ショップの1回の開催 |
| `month` | 同じアカウントのプランをまたいで暦月ごと（アカウントと `sharedKey` と注文日の年月） | SPU、5と0のつく日 |
| `day` | 同じアカウントのプランをまたいで日ごと（アカウントと `sharedKey` と注文日） | 勝ったら倍 |

上限は楽天アカウントごとにかかるので、プランをまたいで共有する上限（`campaign`、`month`、`day`）は、同じアカウントのプランの間だけで共有する。異なるアカウントのプランは、同じキャンペーン、同じ月、同じ日でも上限を共有しない。

`sharedKey` を省いたときは特典の ID をキーにする。プランを作るときに特典を複製しても ID は変わらないので、同じマスタから作った特典は自動的に同じグループになる。同じグループの特典の上限がプランごとに異なるとき（ユーザーが片方だけ編集したとき）は、最も小さい上限を使い、警告を出す。

上限で削った後のポイントは、グループに含まれる全プランの商品へ、生のポイントの比で按分する。各プランの結果には、そのプランの商品に配られた分だけが入る。

### 画面のための計算結果

- `heldEstimates`: 保留中の注文ごとに、その注文の保留を外したときに増える合計ポイント。全プランを計算し直し、全プランの合計の和の差分を取る。上限を共有するプランの間でポイントが移るだけの分は増えたことにしない。
- `shopAroundOutlook`: 買いまわりの特典があるとき、いまのショップ数から10ショップまでの各ショップ数について、倍率と、上限に達するまでに買える残りの金額（税抜と、税率10%として換算した税込の概算。特典の対象額が税込のときは換算しない）。上限は、その特典の上限のグループの上限（食い違うときは最小）から、グループのほかの対象（ほかのプランなど）がすでに得た生のポイントを引いた、このプランに残っている分を使う。「あと1店舗で全商品 +◯倍（約 +◯P）」は、いまのショップ数に1を足したときの倍率で求め、倍率が変わらないときは出さない。

### 計算の手順

1. 商品ごとに、税込の対象額（`unitPrice × quantity − discount`）と、上の式による税抜の対象額を求める。特典の `amountBasis` に応じて、どちらかをその特典の対象額にする。
2. ショップごとに税込の対象額を累計し、`countsTowardShopAround` の購入先について、1,000円以上のショップを数えてショップ数とする。
3. 有効な特典ごとに、適用条件（購入先、ショップ、日付の規則、最低金額）で対象の商品を絞る。`shop-around` の特典では、`receivesShopAround` でない購入先の商品も対象から外す。
4. 特典の種類の計算関数が、商品ごとの生のポイントを求める。`roundingUnit` が `"item"` なら商品ごとに切り捨てる。`"order"` なら注文単位で税抜額を合計して切り捨て、その値を商品の税抜額の比で按分する。
5. 上限の共有範囲（グループ）ごとに、全プランの生のポイントを合計し、上限を超えるときは上限まで削る。削った後のポイントは、商品ごとの生のポイントの比で按分する。購入の順番は結果に影響しない。
6. 合計は内訳の和として求める。

按分はすべて最大剰余法で行い、按分後の商品の値の和が按分前の値と一致するようにする。

ショップ数と上限が注文どうしを結びつけるため、計算は毎回全プランに対して行う。ショップ数はプランごとに数える。注文が数十件の規模なら、全体の再計算で入力の応答に遅れは出ないと見込んでいる。細かい再レンダリングは計算側ではなく Jotai 側で実現する（4節）。

## 4. 状態とデータの流れ

値は「リポジトリ → TanStack Query → Jotai → UI」の一方向に流れる。変更は mutation を通してリポジトリに書き、楽観的更新で TanStack Query のキャッシュに先に反映する。

### リポジトリ（`apps/web/storage`）

インターフェースは `plans.list/get/put/delete`、`profile.get/put`、`shops.list/put` とする。読み書きは必要なレコードだけを対象にし、データベース全体を読み込んだり同期したりはしない。商品を1つ編集したときは、そのプランのレコード1件を書き換える。

IndexedDB は Seitu（`seitu/web` の `createIndexedDb` と `createIndexedDbTable`）で読み書きする。ストアは `plans`、`profile`、`shops`、`quarantine`（検証に失敗したデータの退避先）の4つである。

- 各ストアに `@workspaces/domain` の Valibot スキーマを渡す。Seitu は書き込み時に検証して不正な値を拒否し、読み込み時にも検証する。
- 読み込み時に検証を通らなかったレコードは、`onValidationError` で元のデータを `quarantine` に退避してから捨て、読み込めなかったデータがあることをユーザーに表示する。データは消えてもよい方針なので、退避したデータを復旧する機能は作らない。
- スキーマバージョンは IndexedDB のデータベースの版として持つ。データの形を変えるときは版を上げ、`onUpgrade` の `migrate(store, rewrite)` で `domain/migrations` の変換関数を古い版から順に全レコードへ適用する。変換は1つのトランザクションで行われるので、途中で失敗するとデータベース全体が元の版に戻る。
- マイグレーションに失敗すると、Seitu はデータベースを古い版のまま残し、以後の読み書きをすべて失敗させる。この場合はデータベースを削除して作り直し、データを初期化したことをユーザーに表示する。
- Seitu の `query()`（変更の購読）と React 向けの部品は使わない。変更の購読は TanStack Query と Jotai が受け持ち、Seitu にも購読させると正しい値の置き場所が2つになるからである。

Seitu は1人の作者が開発する比較的新しいライブラリ（採用時点で v1.3.1）である。リポジトリの実装の中だけで使うので、問題が出たときの差し替えはリポジトリの実装に閉じる。

将来の D1 保存では、このインターフェースの D1 実装を追加する。ログインした利用者は D1 を、ログインしない利用者は IndexedDB を使い、ログイン時に IndexedDB のデータを D1 へ移す。

### TanStack Query

クエリキーは `["plans"]`、`["plan", id]`、`["profile"]`、`["shops"]` とする。注文の追加、商品の編集、特典の切り替えなどの変更は、プラン全体を書き換える mutation として実装する。

### Jotai（`apps/web/state`）

- jotai-tanstack-query の `atomWithQuery` でプランを atom にする。
- 注文ごと、商品ごと、特典ごとの派生 atom を `atomFamily` で作り、値が等しければ再描画しないよう等価判定を付ける。
- 計算結果は `calculationAtom = atom((get) => calculateAll(get(plansAtom), get(shopsAtom)))` で全プランについて求める（上限をプラン間で共有するため）。表示中のプランの結果と内訳の行ごとの atom は、その結果から自分の分だけを取り出す。
- Jotai が自分で値を持つのは、選択中のプラン ID や開いているパネルなど、UI の一時的な状態だけである。

### Formisch

フォームは注文1件ごとに1つ作り、入力中の値はフォームが持つ。値が Valibot の検証を通り、かつフォーカスが外れたとき、または入力が 300ms 止まったときに mutation を呼ぶ。計算は保存済みの値から行うので、入力途中の不正な値は計算に入らない。

## 5. 画面とルート

全ページを事前レンダリングする。ユーザーのデータは端末にしかないため、HTML には外枠と静的な内容だけが入り、データの部分はブラウザで読み込んだあとに描画する。

| パス | 内容 | 静的に入る内容 |
|---|---|---|
| `/` | プランの一覧と新規作成。開催中・開催予定の公式イベントを案内する | 公式イベント、お知らせ、広告 |
| `/plan?id=…` | プランの詳細。注文のカード一覧（追加、編集、コピー、並べ替え、保留、削除）、特典のパネル（SPU とキャンペーンの ON/OFF と、倍率・上限の上書き）、結果（合計、上限の到達状況、ショップ数、商品ごとの内訳） | 広告 |
| `/profile` | SPU の設定とショップ台帳 | SPU の標準定義 |
| `/inquiry` | 問い合わせフォーム | なし |
| `/terms` | 利用規約 | 本文 |

プランの詳細は `/plan/$id` ではなく `/plan?id=…` にする。パスにプラン ID を入れると、ビルド時に存在しないパスを Worker で描画する必要が生じるが、クエリパラメータにすれば事前レンダリングした1枚の HTML ですべてのプランを表示できる。

共通のレイアウトは、ヘッダー、フッター、共有ボタン、ビルド時に生成した広告枠、Google Analytics、AdSense からなる。最初の表示のページビューは gtag の `config` が送り、画面遷移のページビューは GA4 の拡張計測（「ブラウザの履歴イベントに基づくページの変更」）が送る。アプリはページビューを自分で送らないので、この設定は ON のままにする。スマートフォンの画面幅を基準にし、PC では結果のパネルを横に置く。

## 6. 外部との連携

### 楽天 API の共通部分

新しい API（`openapi.rakuten.co.jp`）を使う。`applicationId`、`accessKey`、`affiliateId` は環境変数で渡して Valibot で検証する。レスポンスも Valibot で検証し、必要なフィールドだけを取り出す。

呼び出しは `apps/web/src/rakuten/` にまとめ、ブラウザ（商品情報の取得）とビルド時（広告）の両方から使う。

- `config.ts`: 環境変数 `PUBLIC_RAKUTEN_APPLICATION_ID`、`PUBLIC_RAKUTEN_ACCESS_KEY`、`PUBLIC_RAKUTEN_AFFILIATE_ID` の検証。値が足りないか `encrypted:` のままのときは、商品情報の取得を無効にしてビルドを続ける。ビルドは検証した値をクライアントに埋め込む
- `item-search.ts`: 商品検索 API の呼び出し。失敗は通信エラー、429、その他の HTTP エラー、想定外のレスポンス、該当なしに分けて返す。サーバーから呼ぶときは `Origin: https://point-sprint.bmth.dev` を付ける
- `item-lookup.ts`: 呼び出しの間隔を1.1秒以上あけ、見つかった商品を商品ページ（ショップコードと商品管理番号）ごとに5分間キャッシュする

### 環境変数

環境変数はリポジトリのルートの `.env.development`（`pnpm dev`）と `.env.production`（`pnpm build`）に置き、どちらもコミットする。ファイル名の末尾の環境名は dotenvx の決まりに合わせたもので、`.env.production` は鍵 `DOTENV_PRIVATE_KEY_PRODUCTION` で復号する。

- 公開してよい値は変数名を `PUBLIC_` で始め、平文で置く（`dotenvx set … --plain`）。楽天 API の3つの値（`PUBLIC_RAKUTEN_*`）と Turnstile のサイトキー（`PUBLIC_TURNSTILE_SITE_KEY`）がこれにあたる。
- 秘密の値（`TURNSTILE_SECRET_KEY`、`INQUIRY_TO_ADDRESS`、`CLOUDFLARE_API_TOKEN`）は `.env.production` に dotenvx で暗号化して置く。`.env.development` には秘密の値を置かず、Turnstile は Cloudflare のテスト用キーを、`INQUIRY_TO_ADDRESS` は仮のアドレスを平文で置く。
- Worker が使う秘密の値（`TURNSTILE_SECRET_KEY`、`INQUIRY_TO_ADDRESS`）は `cloudflare.config.ts` で `bindings.secret()` として宣言する。ローカル（`pnpm dev`、`vite preview`）では Cloudflare の Vite プラグインが環境変数から値を取る。値はビルドの出力には入らないので、本番の Worker への登録は計画4で行う。
- 秘密鍵は `.env.keys` に置き、コミットしない。デプロイでは GitHub の Secret `DOTENV_PRIVATE_KEY_PRODUCTION` から渡す。
- `pnpm dev` と `pnpm build` は `dotenvx run` でファイルを読む。`vite.config.ts` は `PUBLIC_` で始まる値だけを Vite の `loadEnv` でルートのファイルから直接読み、クライアントに渡す。鍵がなくても（PR の CI やプレビューでも）公開の値はビルドに入る。

### 商品情報の取得

ブラウザから次の順で行う。

1. 購入先のパーサーが、URL からショップコードと商品管理番号を取り出す。
2. ショップ台帳とショップコードで照合し、台帳になければショップを登録する。
3. 購入先が商品情報の取得に対応し（楽天市場だけ）、URL から商品管理番号が取り出せたときだけ、商品検索 API を呼ぶ。API の `itemCode` は商品管理番号とは別の値なので、ショップコードと商品管理番号（キーワード）で検索し、商品ページの URL が一致する商品を使う。商品管理番号が検索の対象になっていない商品は見つからず、自動入力できない。商品名、税込の単価、ショップ（台帳になければショップ名とショップコードで登録）、ショップ独自倍率（`pointRate` が2以上のとき）を注文の入力欄に入れる。入れた値はユーザーが編集できる。税別の価格（`taxFlag` が1）は単価に入れない。

注文に保存する商品 URL は、アフィリエイトリンクではなく、ユーザーが貼った商品 URL にする。アフィリエイトリンク（`hb.afl.rakuten.co.jp`）は購入先のパーサーで読めないため、保存すると、編集のときに URL からショップを判定できなくなるからである。今の画面には保存した URL へのリンクを出す場所がないので、アフィリエイトリンクを持つ利点もない。商品へのリンクを出すときは、そのときにアフィリエイトリンクを組み立てる。

通信エラー、商品が見つからない、レート制限のいずれかで手順3が失敗したときは、手順1と2の結果を残し、自動入力できなかったことを表示する。楽天 API は `Origin` ヘッダーがアプリ設定の「許可された Web サイト」（`https://point-sprint.bmth.dev`）と一致するときだけ応答する。`Origin` はサーバー側から自由に付けられるので、`accessKey` は公開されてもよい値として扱う。開発中は `localhost` が許可されないため、開発サーバー（Vite の `server.proxy`）で `/rakuten-api` への呼び出しを API に中継し、`Origin` を付け替える。本番では中継せず、ブラウザから API を直接呼ぶ（検証結果は `docs/superpowers/spikes/2026-10-04-external-integrations.md`）。

### 広告

ルートの loader でビルド時に商品検索 API を呼び、結果を HTML に埋め込む。API の呼び出しが失敗したときはビルドを止めず、広告枠を空にする。広告が出ないことは、サイト全体の公開を止める理由にならないからである。広告はデプロイのときだけ更新する。

### 問い合わせ

1. `/inquiry` の Formisch のフォーム（名前は任意、返信先のメールアドレスと本文は必須。返信を希望するかのチェックボックスもある）で入力を Valibot で検証し、Turnstile のウィジェットからトークンを受け取ってから、サーバー関数（`apps/web/src/server/submit-inquiry.ts`）を呼ぶ。トークンを受け取るまでは送信できない。
2. サーバー関数は、入力を同じスキーマで検証し直し、Turnstile のトークンを `siteverify` で検証してから、`send_email` バインディング（`INQUIRY_EMAIL`）で `inquiry@bmth.dev` から運営者に送る。利用者のアドレスは `Reply-To` に入れる。メール（生の MIME、件名は B エンコード、本文は base64）は純粋関数で組み立てる。
3. 失敗は、入力（`input`）、設定の不足（`config`）、Turnstile（`turnstile`）、送信（`send`）のどの段階かを返し、ログには段階とエラーコードだけを残す。本文やメールアドレスはログに残さない。
4. 利用者には段階によらず「送信できませんでした」と出し、入力を残したまま、Turnstile の確認をやり直して再送できるようにする。

宛先の運営者のアドレスは、Email Routing で確認済みの宛先を Worker の秘密の値 `INQUIRY_TO_ADDRESS` で渡し、コードや公開のファイルには書かない。`send_email` は Email Routing の確認済みの宛先にしか送れないので、バインディングでは宛先を制限せず、送信元だけを `inquiry@bmth.dev` に制限する。

Worker の実行環境に依存する部分（`cloudflare:workers` の `env`、`cloudflare:email`）は `worker-inquiry.ts` に分け、サーバー関数のハンドラーの中で読み込む。テストでは段階ごとの処理（`inquiry.ts`）に `siteverify` と `send_email` の代わりを渡し、外部には送らない。`pnpm dev` では `.env.development` の Turnstile のテスト用キーで `siteverify` まで通り、`send_email` はローカルで模擬される（`.eml` ファイルに書き出される）。E2E では Turnstile のスクリプトを差し替え、プレビューの Worker には秘密の値を渡さないので、サーバー関数は `config` の段階で止まる。

### 実装計画の最初に行う検証

次のどれかが成り立たないときは、この節を見直す。

- ブラウザから商品検索 API を呼べるか。CORS が使えなければ JSONP（`callback` パラメータ）で呼べるか
- ビルド時（サーバー側）から、Referer の制限を受けずに商品検索 API を呼べるか
- `send_email` と Turnstile が、使う予定のドメインで動くか

## 7. テスト

### `packages/domain`

テストを最も厚くするパッケージである。

- 計算エンジン: 3節の「計算が従う楽天の規則」と、その出典の計算例をテストケースにする。上限への到達、1,000円の境界と同じショップでの累計、0と5のつく日の判定、端数の単位（商品ごとと注文ごと）、クーポン、按分の端数、ラクマ（数えるが倍率は乗らない）などを含める。期待値は手計算か公式の例から決め、テストに根拠（出典やメモ）を書く。
- 特典の種類と購入先: 種類ごとの計算関数を単体テストする。URL のパーサーには、楽天市場、楽天ブックス、ラクマの実際の URL の形を与える。
- マイグレーション: スキーマバージョンごとの保存データのサンプルを残し、変換関数を順に適用して最新版まで移行できること、移行後のデータが Valibot の検証を通ることを確かめる。変換関数は純粋関数なので、IndexedDB なしでテストできる。
- マスタデータ: すべてのデータファイルがスキーマの検証を通ることを、テストとビルドの両方で確かめる。

### `apps/web`

- Vitest の単体テスト: リポジトリの IndexedDB 実装（`fake-indexeddb` を使う）と、楽天 API のレスポンスの検証と変換。リポジトリでは、古い版のデータベースを開いたときの移行、検証に失敗したレコードの退避、移行に失敗したときの作り直しを確かめる。
- Vitest のブラウザモード: 注文カードの入力から mutation が呼ばれる流れ。1つの商品を編集したとき、ほかの行が再描画されないこと（R1 の回帰テスト。描画回数を数える）。

### Playwright

主な流れだけを確かめる。

- プランの作成、注文の追加、結果の表示
- 再読み込み後もデータが残っていること

### CI

プルリクエストごとに、oxlint、oxfmt のチェック、型チェック、cspell、Vitest を実行する。Playwright は main へのマージ前に実行する。テストでは外部 API をモックにし、実際の API は「実装計画の最初に行う検証」で手動で確かめる。
