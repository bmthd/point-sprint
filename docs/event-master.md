# 公式イベントのマスタ

公式イベント（お買い物マラソン、ブラックフライデーなど）のマスタは、D1 のデータベース `point-sprint-events` の表 `official_events` にある。Worker の Cron Triggers が楽天の告知ページから収集し、検査を通った回だけを公開する。トップページは Worker が描き、公開中のイベントを HTML に入れて返す。描いた HTML は、ビルドと今日とイベントの中身から作るキーでデータセンターのキャッシュに置く（`apps/web/src/server/official-events/top-page-cache.ts`）。Cron がイベントを書き換えるとキーが変わるので、どのデータセンターでも次のリクエストから新しい一覧が出る。キーには日本の今日も含め、「開催中」などのバッジとタブの振り分けもその日で描く。ハイドレーションの後は、ブラウザの今日に合わせる。デプロイしなくても、収集した回はトップページに出る。プランの設定などは、Worker が返す `/events.json` を読む。お買い物マラソンの日程と上限のページ（`/marathon`）も、Worker がリクエストのたびにマスタから描くので、デプロイしなくても新しい回が HTML に入る。

大型の期間イベント（ブランドデーなど）も収集しない。回が告知されたら、運営者が「大型の期間イベント」の手順で行を足す。

## 収集のしくみ

Worker（`apps/web/src/server/official-events/collect-events.ts`）が、日本時間の 10:00〜10:55 の 5 分おきと、16:05、22:05、04:05 に次の4ページを読む。告知はエントリー開始の 10:00 に出るので、その 1 時間だけ細かく読み、告知から 5 分以内にトップページに出す。1回の取得は4ページだけにする。User-Agent は一般的なブラウザのものを使う。

| ページ | URL | 読むもの |
|---|---|---|
| お買い物マラソンのスケジュール | https://event.rakuten.co.jp/campaign/point-up/marathon/schedule/ | その月の各回の名前（「第二弾」）と期間 |
| お買い物マラソン | https://event.rakuten.co.jp/campaign/point-up/marathon/ | エントリー開始（開催の2日前の 10:00 ごろ）から終了までの回の、ポイントアップ期間、倍率、獲得上限 |
| ブラックフライデー | https://event.rakuten.co.jp/campaign/point-up/blackfriday/ | 告知から終了までの、キャンペーン名、ポイントアップ期間、倍率、獲得上限 |
| 楽天スーパーSALE | https://event.rakuten.co.jp/campaign/supersale/ | 告知から終了までの、キャンペーン名、ポイントアップ期間、倍率、獲得上限 |

- 終了日が今日以降の回を、`marathon-<開始日>` の `id` で書き込む。一度公開した `id` は変えない。保存されたプランが `officialEventId` で参照している。
- マラソンのページにまだ出ていない回は、スケジュールのページの期間と、ガイドの倍率（10ショップで最大10倍）で公開し、上限は空にする。トップページには「上限は未発表」と出る。マラソンのページに出たら、そのページの倍率と上限で上書きする。
- スケジュールのページより先に、マラソンのページが新しい月の回を出すことがある（2026-11-02 には、スケジュールのページが 10 月の 3 回のままで、マラソンのページは 11 月 4 日からの「お買い物マラソン&ジャンル祭」を出していた）。マラソンのページの回が、スケジュールのページのどの回とも期間が重ならなければ、マラソンのページの期間・時刻・倍率・上限で公開する。名前はキャンペーン名（「お買い物マラソン&ジャンル祭」）にし、収集の記録に「スケジュールのページにまだない回を、マラソンのページから追加」と残す。スケジュールのページに同じ期間の回が載ったら、`id` と特典の `id` はそのままで、名前を「お買い物マラソン第一弾」などに更新する。
- スケジュールのページには、各回の上限の行がコメントアウトされて残っている。この行は実際と違うことがある（2026年10月の第一弾は「10,000ポイント」とあったが、開催中のページでは 7,000 ポイントだった）ので、読まない。
- ブラックフライデーは、マラソンと同じショップ買いまわりで、ページの「キャンペーン詳細」も同じ作りをしている。`black-friday-<開始日>` の `id` で、名前はキャンペーン名（「楽天市場のブラックフライデー」）にする。スケジュールのページはないので、このページに出てから公開する（2026 年は、11-19 からの回が 11-15 には出ていた）。年の大半は回がないので、ページが取れなくても、回が出ていなくても、警告にはしない。

  | 年 | エントリー開始 | ポイントアップ期間 |
  |---|---|---|
  | 2020 | 11-15 10:00 | 11-19 20:00〜11-24 01:59 |
  | 2021 | 11-16 10:00 | 11-18 20:00〜11-23 01:59 |
  | 2022 | 11-18 10:00 | 11-22 20:00〜11-27 01:59 |
  | 2023 | 11-17 10:00 | 11-21 20:00〜11-27 01:59 |
  | 2024 | 11-17 10:00 | 11-21 20:00〜11-27 01:59 |
  | 2025 | 11-12 10:00 | 11-20 20:00〜11-27 01:59 |
  | 2026 | 11-12 10:00 | 11-19 20:00〜11-25 01:59 |

  告知ページは、エントリー開始からその年の回を出す（Wayback Machine の版で確かめた）。ページの作りは毎年変わる（2023・2024 は `rc-campaignRules`、2025 は上限が `<div>` に入っていた）ので、読めない年は手で行を足す。
- 楽天スーパーSALE も同じショップ買いまわりで、3・6・9・12 月の 4 日 20:00〜11 日 01:59 に開かれる。告知ページは、エントリー開始（2026-12 は 11-28 10:00）からその回を出す。ページの「キャンペーン詳細」には、楽天モバイル利用者の先行セール、楽天モバイル利用者の買いまわり（先行セールの日から）、全員の買いまわりの 3 つが並ぶ。収集は、キャンペーン名に「楽天モバイル」を含むものを読まず、全員の買いまわりを `supersale-<開始日>` の `id` と、キャンペーン名（「楽天スーパーSALE」）で書き込む。回のない時期は、ブラックフライデーと同じく警告にしない。
- 期間の初日の開始時刻と最終日の終了時刻（「20:00」「01:59」）は、`period_start_time` と `period_end_time` に入れる。トップページに出し、プランでは初日・最終日の注文に「この時刻の外の注文は対象外」と注意を出す。プランの計算は日付だけで判定する（#69）。
- 楽天のショッピング規約の第7条（禁止事項）は、自動化された手段での商品の購入（「商品ページ上の情報取得等を含む」）と、サーバーへの過度の負担を禁じている。告知ページを読むこと自体を禁じる条文はない（2026-10-17 に確認）。商品ページは読まない。

## 公開してよいかの検査

次のどれかに当たる回は公開しない。すでに公開している回は前の内容のまま残し、まだない回は `pending` で書き込む。

- `OfficialEventSchema` の形に合わない
- 期間が 2〜14 日の範囲にない
- 倍率（通常の1倍を含む）が 1〜20 倍の範囲にない
- 上限が 1,000〜100,000 ポイントの範囲にない
- マラソンのページの期間が、スケジュールのページのどの回とも一致せず、どれかの回と重なる（読み違えたおそれがある）
- マラソンのページのキャンペーン名が「お買い物マラソン」で始まらない
- ブラックフライデーのページのキャンペーン名に「ブラックフライデー」がない
- スーパーSALE のページのキャンペーン名に「スーパーSALE」がない

ページの作りが変わって読めないときも、その回は書き込まない。

## 担当と気づき方

- 担当はリポジトリの運営者。
- 収集のたびに、表 `collection_runs` に結果（`ok`、`warning`、`failed`）と理由を残す。
- 毎日 9:00 に、ワークフロー「Event master」（`.github/workflows/event-master.yml`）が `https://point-sprint.bmth.dev/events.json` を調べる。7 日後まで続くイベントが 1 つもないか、読めないと、Issue「公式イベントの収集を確かめる」を立てる。同じ題の Issue が開いていれば、新しく立てずに、その Issue に検査の結果と実行の URL をコメントで足す。
- 毎年 11-19〜11-27 は、今年のブラックフライデー（`black-friday-` の `id`）が配信されていなければ、同じ Issue を立てる。告知ページの作りは毎年変わるので、読めなくなったことにここで気づく。
- 3・6・9・12 月の 3 日〜10 日は、その月の楽天スーパーSALE（`supersale-` の `id`）が配信されていなければ、同じ Issue を立てる。
- スケジュールのページは月ごとなので、月末の回が終わってから翌月のページが出るまでの間も Issue が立つことがある。そのときは翌月のスケジュールのページが出ているかを確かめる。

## Issue が立ったら

収集の記録を新しい順に見る。`apps/web` で実行する。

```sh
pnpm exec cf d1 query <データベースの ID> --sql "SELECT * FROM collection_runs ORDER BY id DESC LIMIT 10"
```

データベースの ID は `apps/web/cloudflare.config.ts` の `EVENTS_DB` にある。

- `failed` が続くとき: スケジュールのページが取れないか、読めない。ページを開いて作りが変わっていないかを確かめ、`apps/web/src/server/official-events/event-pages.ts` を直す。直したら、そのときのページを `apps/web/src/server/official-events/event-pages/` に固定してテストを足す。
- `warning` のとき: メッセージにある理由を見る。楽天の告知が正しく、検査が厳しすぎるなら検査を直す。
- `ok` が続くのに次の回がないとき: `official_events` に `pending` の行がないかと、公式ページに次の回の告知があるかを確かめる。告知がなければ日付を予測して足さず、確認日時と公式ページの状態を Issue に残す。

## 行を直すとき

誤った内容が公開されたときや、収集できない回を足すときは、行を直接直す。直した行は `locked = 1` にする。収集は `locked` の行と `rejected` の行を上書きしない。

```sh
# 公開をやめる
pnpm exec cf d1 query <ID> --sql "UPDATE official_events SET status = 'rejected', updated_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now') WHERE id = 'marathon-2026-10-24'"

# 上限を直して固定する
pnpm exec cf d1 query <ID> --sql "UPDATE official_events SET benefits_json = json_set(benefits_json, '$[0].params.cap', 7000), locked = 1, updated_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now') WHERE id = 'marathon-2026-10-24'"
```

- 出典にするのは楽天の公式のページだけにする。まとめサイトや個人のブログの「予想」は使わない。
- `benefits_json` は `OfficialEventSchema` の `benefits` の形にする。形に合わない行は配信しない。
- 特典の `id` は UUID にする（`uuidgen | tr A-Z a-z`）。
- 終わったイベントは消さない。そのイベントから作ったプランが、名前の表示などに使っている。

## 大型の期間イベント

期間中の合計額（税込）で倍率が決まる 2〜3 日のイベント。特典は `spend-tiers` で表し、`params.tiers` に「合計額の下限（円）→ 上乗せの倍率」を並べる。倍率は公式の「ポイント N 倍」から通常の 1 倍を引いた値にする。上限は開催ごとなので、`capScope` は `"campaign"`、`sharedKey` は行の `id` にする（マラソンと同じ）。

| イベント | 出典にするページ | `id` | 回ごとに確かめること |
|---|---|---|---|
| 楽天ブランドデー | https://event.rakuten.co.jp/brand/campaign/ | `brand-day-<開始日>` | 期間、段階（2026-10 は 30,000 円未満で +2 倍、以上で +4 倍）、上限（4,000）。対象は対象アイテムだけなので、`conditions.orderTags` を `["brand-day"]` にする |
| 楽天イーグルス感謝祭 | https://event.rakuten.co.jp/campaign/eagles/thanks/ | `eagles-thanks-<開始日>` | 期間、段階。最上段の金額が回ごとに違う（2024 は 50,000 円、2025 は 45,000 円で +4 倍）。上限（5,000） |
| 新春ポイントアップ祭 | https://event.rakuten.co.jp/newyear/campaign/pointup/ | `newyear-pointup-<開始日>` | 期間（1 月 1〜3 日）、段階（2026 は 5,000・10,000・30,000・45,000 円で +1・+2・+4・+6 倍）、上限（5,000） |
| 超ポイントバック祭 | https://event.rakuten.co.jp/campaign/pointback/ | `pointback-<開始日>` | 期間、段階。回ごとに違う（2026-05 は 5 段で最大 +5 倍、2025-12 は 4 段で最大 +4 倍）。上限（5,000） |

- 段階は毎回、公式ページの「キャンペーン詳細」の「特典内容」から写す。前の回の値を使い回さない。
- ブランドデーは、ページ上部と「キャンペーン詳細」で条件金額が食い違ったことがある（上部に「期間中のお買い物金額合計10,000円(税込)以上」とあった）。「キャンペーン詳細」の「特典内容」に従う。2026-10 の回は、上部の行が HTML のコメントになっていて、特典内容に下限がないので、最初の段を 0 円にした。この回は `apps/web/migrations/0002_brand_day_2026_10.sql` で入れた。
- 期間は「ポイントアップ期間」。エントリー期間ではない。時刻もこの期間のものを `period_start_time` と `period_end_time` に入れる。分からなければ空にする。プランには「時刻によっては対象外」と出る。
- 超ポイントバック祭は告知なしで始まり、マスタに入るまでに開催の一部が過ぎる。その間は、プランの設定のキャンペーン「超ポイントバック祭」（直近の回の段階が入ったテンプレート）を足し、段階を直してもらう。
- バナーは `.webp` にして R2 の `/img/campaign/` に置き、特典の `imagePath` に書く。

行は次の形で足す。特典の `id` は UUID にする。

```sh
pnpm exec cf d1 query <ID> --sql "INSERT INTO official_events (id, name, period_start, period_end, period_start_time, period_end_time, benefits_json, source_url, locked, status) VALUES ('pointback-2026-05-19', '超ポイントバック祭', '2026-05-19', '2026-05-20', NULL, NULL, '[{\"id\":\"<UUID>\",\"kind\":\"spend-tiers\",\"category\":\"campaign\",\"label\":\"超ポイントバック祭\",\"enabled\":true,\"amountBasis\":\"tax-excluded\",\"capScope\":\"campaign\",\"sharedKey\":\"pointback-2026-05-19\",\"conditions\":{\"dateRule\":{\"type\":\"range\",\"start\":\"2026-05-19\",\"end\":\"2026-05-20\"}},\"params\":{\"tiers\":[{\"minAmount\":5000,\"rate\":1},{\"minAmount\":10000,\"rate\":2},{\"minAmount\":20000,\"rate\":3},{\"minAmount\":40000,\"rate\":4},{\"minAmount\":60000,\"rate\":5}],\"cap\":5000,\"roundingUnit\":\"item\"}}]', 'https://event.rakuten.co.jp/campaign/pointback/', 1, 'published')"
```

`benefits_json` に新しい `orderTags` の値を使う行は、その値を読めるアプリをデプロイしてから足す。前の版の Worker は、読めない行を配信しない。

## 楽天スーパーSALE の先行セール

楽天スーパーSALE の前日には「楽天モバイルご利用者限定 先行セール」がある（2026-12 の回は 12-03 20:00〜12-04 19:59）。先行セールで買った注文も、楽天モバイルの利用者だけショップ買いまわりの対象になる。利用者のポイントアップ期間は先行セールの開始から、それ以外の人はお買い物期間の開始からになる。

- 行の `id` と、特典の `sharedKey` は `supersale-<開始日>`（2026-12 の回は `supersale-2026-12-04`）にする。開始日はお買い物期間の初日。
- 行の期間（`period_start`・`period_end`、時刻の列）は、お買い物期間（ポイントアップ期間）にする。2026-12 の回は `2026-12-04` 20:00〜`2026-12-11` 01:59。
- 先行セールは、ショップ買いまわりの特典の `conditions.presale` に書く。`start`・`end` は先行セールの初日と最終日、`times` はその時刻、`spuBenefitId` は SPU の「楽天モバイル」の `id`（`ca794fa7-4a85-43c6-ab34-e06feb115c5d`、`packages/domain/src/master/spu.ts` の `MOBILE_SPU_ID`）にする。`dateRule` はお買い物期間のままにする。
- プランは、先行セールの初日から始まる。プランの月（先行セールの初日の月）の SPU で楽天モバイルが ON なら、買いまわりの日に先行セールの日を足して計算する。ラクマ購入 +1倍は「12月4日(金)20:00からのお買い物が対象」なので、先行セールの日を足さない。OFF なら先行セールの日の注文を買いまわりから外し、「SPU の楽天モバイルが OFF なので対象外」と出す。トップページのイベントには「楽天モバイルの利用者は 12/3（木）20:00 から」と出る。
- 先行セールの対象者（Rakuten最強プランなどの利用者で、前日の 23:59 までに利用を始めた人）と、エントリー不要であることは、公式ページで確かめるだけにする。アプリは SPU の楽天モバイルで判定する。

```json
{"id":"<UUID>","kind":"shop-around","category":"campaign","label":"ショップ買いまわり","enabled":true,"amountBasis":"tax-excluded","capScope":"campaign","sharedKey":"supersale-2026-12-04","conditions":{"dateRule":{"type":"range","start":"2026-12-04","end":"2026-12-11"},"presale":{"start":"2026-12-03","end":"2026-12-04","times":{"start":"20:00","end":"19:59"},"spuBenefitId":"ca794fa7-4a85-43c6-ab34-e06feb115c5d"}},"params":{"tiers":[{"minShops":2,"rate":1},{"minShops":3,"rate":2},{"minShops":4,"rate":3},{"minShops":5,"rate":4},{"minShops":6,"rate":5},{"minShops":7,"rate":6},{"minShops":8,"rate":7},{"minShops":9,"rate":8},{"minShops":10,"rate":9}],"cap":7000,"roundingUnit":"item"}}
```

`conditions.presale` を使う行は、それを読めるアプリをデプロイしてから足す（前の版の Worker は、知らないキーを捨てて先行セールのない回として配信する）。

## 表の形を変えるとき

`apps/web/migrations/` に SQL を足す。本番には Deploy のワークフローが、Preview には Preview のワークフローがデプロイの前に当てる。手元の開発サーバーと E2E は、起動のたびにローカルの D1 を作り直して当てる（`pnpm --filter web db:migrate --local`）。開発サーバーは、起動したまま足されたマイグレーションも、次に D1 を読むときに当てる（`apps/web/src/server/shared/dev-migrations.worker.ts`）。
