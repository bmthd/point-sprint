# 用語集

ポイント計算ツールの設計とコードで使う用語を定める。コード上の識別子は「英語名」の列に揃える。

状態の列は、設計の議論で確定した用語を「確定」、定義がまだ動きうる用語を「検討中」とする。

## 計画と記録

| 用語 | 英語名 | 状態 | 定義 |
|---|---|---|---|
| プラン | `Plan` | 確定 | ユーザーが作る買い物計画で、購入記録をまとめる最上位の単位。公式イベントを参照して作ることも、参照せずに普段の買い物を記録することもできる。 |
| 公式イベント | `OfficialEvent` | 確定 | プランを作るときに選べるプリセット。お買い物マラソンや楽天スーパーSALEのように、楽天が開催するイベントの定義。ビルド時に静的データとして配信し、期間と、そのイベントで使える特典の一式を含む。プランを作るときのひな形であり、プランから参照されても書き換えられない。 |
| プロフィール | `Profile` | 確定 | ユーザー自身の SPU の達成状況など、プランをまたいで使う設定。プランを作るときにスナップショットとしてプランへ複製する。 |
| 楽天アカウント | `Account` | 確定 | 計算のために見分ける楽天のアカウント。利用者が付けた名前だけを持ち、認証情報は扱わない。プランごとに購入するアカウントを決め、プランをまたぐ上限は同じアカウントのプランの間だけで共有する。既定のアカウント「メイン」があり、複数のアカウントを使い分ける設定を有効にするまでは、すべてのプランが既定のアカウントのものになる。 |
| スナップショット | `Snapshot` | 確定 | プラン作成時に、プロフィールや公式イベントの内容をプランへ複製したもの。複製後に元を変更しても、作成済みのプランの計算結果は変わらない。 |

## 特典

| 用語 | 英語名 | 状態 | 定義 |
|---|---|---|---|
| 特典 | `Benefit` | 確定 | ポイントを上乗せする規則の1件で、特典の種類と、その種類が要求する値（倍率、上限、対象条件、期間など）からなる。データとして保存し、ユーザーが編集できる。SPU の項目もキャンペーンも特典として表し、計算エンジンは両者を区別しない。 |
| 特典の種類 | `BenefitKind` | 確定 | 特典の計算方法の型。「上限付きの倍率加算」「ショップ数に応じて段階的に増える倍率」など、コードで定義して単体テストで検証する。新しい計算方法が必要になったときは、特典の種類を拡張点に1つ追加する。ユーザーは種類を作れず、既存の種類を選んで値を編集する。 |
| SPU | `Spu` | 確定 | 楽天のサービス利用状況に応じて常時上乗せされる倍率（スーパーポイントアッププログラム）。画面では SPU として分けて表示するが、データ上はプロフィールに属する特典の集まりである。 |
| キャンペーン | `Campaign` | 確定 | 期間や条件を限って上乗せされる特典（0と5のつく日、39ショップなど）。画面では SPU と分けて表示するが、データ上はプランに属する特典である。 |
| 買いまわり | `ShopAround` | 確定 | お買い物マラソンなどで、購入したショップ数に応じて倍率が段階的に上がる特典。ショップ数の数え方は「ショップ数」の項を参照。 |
| 上限 | `Cap` | 確定 | 1つの特典で獲得できるポイントの最大値。上限を超えた分は付与されない。上限は購入の順番によらず、特典の合計に対してかかる。 |
| 上限の共有範囲 | `capScope` | 確定 | 特典の上限をどの単位でかけるか。`plan`（プランごと）、`campaign`（プランをまたいで1つ）、`month`（プランをまたいで暦月ごと）、`day`（プランをまたいで日ごと）、`occurrence`（プランをまたいで開催ごと。開催は特典の日付で見分ける）のいずれか。プランをまたぐ範囲は、同じ楽天アカウントのプランの間に限る。SPU と5と0のつく日は `month`、勝ったら倍は `occurrence`、お買い物マラソンと39ショップは `campaign` である。 |
| 共有キー | `sharedKey` | 確定 | プランをまたいで上限を共有する特典を同じグループにまとめるキー。省略時は特典の ID を使う。 |
| 排他グループ | `exclusiveGroup` | 確定 | 同時に1つしか有効にできない特典のまとまり。楽天カードと楽天プレミアムカードの特典分のように、利用者の契約によってどちらか一方だけが当てはまる SPU に使う。 |
| 前提の特典 | `requires` | 確定 | その特典が前提にする特典の ID。前提の特典は、それを前提にする特典のどれかが有効なときだけ有効になる。前提にする特典を有効にすると前提の特典も有効になり、有効なものがなくなると前提の特典も無効になる。前提の特典を有効にしたとき、前提にする特典がどれも無効なら最初の1つを有効にし、前提の特典を無効にすると前提にする特典もすべて無効になる。楽天カード特典分と楽天プレミアムカードの特典分が、楽天カード通常分を前提にする。 |
| 対象額の基準 | `amountBasis` | 確定 | 特典のポイントを税抜の対象額で計算するか、税込の対象額で計算するか。既定は税抜で、楽天カード通常分だけが税込である。 |
| 楽天カード通常分 | — | 確定 | 楽天カード本体の還元（1倍）。1注文ごとの決済額を税込で対象にし、上限はない。SPU の楽天カード特典分（+1倍、税抜、月間上限あり）とは別の特典である。 |
| 定例キャンペーン | `CampaignTemplate` | 確定 | 5と0のつく日、勝ったら倍、39ショップ、リピート購入のように繰り返し開催されるキャンペーンのひな形。日付が決まっているものは日付の規則で判定し、決まっていないものはユーザーが開催日や期間を入れて特典を作る。マスタの更新が止まっても使えるように、買いまわりと自由な倍率加算のテンプレートも持つ。 |
| ショップ属性 | `ShopTag` | 確定 | ショップが持つ属性。最初のリリースでは `39shop`（39ショップ）だけ。適用条件 `shopTags` で使う。 |

## 購入

| 用語 | 英語名 | 状態 | 定義 |
|---|---|---|---|
| 注文 | `Order` | 確定 | 1つのショップで行う1回の購入で、入力の単位でもある。ショップ、日付、1件以上の商品を持つ。日付によって適用される特典（0と5のつく日など）は、注文日で判定する。同じショップへの注文を複数作ることができ、それらはショップの同一性によって同じショップへの注文として扱う。 |
| 商品 | `LineItem` | 確定 | 注文に含まれる1品目。名前、税込の単価、数量、税率（10%、8%、非課税）、クーポンの値引額を持つ。ポイントは原則として商品ごとに「税抜の対象額 × 倍率」を求めて端数を切り捨てる。注文は通常1件の商品を持ち、必要に応じて複数の商品を追加できる。 |
| 保留 | `onHold` | 確定 | 注文を計算から外しておく状態。保留中の注文は買い回りのショップ数にも合計にも入らず、画面では含めた場合のポイントを取り消し線で参考に出す。 |
| 注文の属性 | `OrderTag` | 確定 | 注文が持つ属性。最初のリリースでは `repeat`（リピート購入）だけ。適用条件 `orderTags` で使う。 |
| コピー | `copyOrder` | 確定 | 注文と、その中の商品の ID を新しくして、同じ内容の注文を元の直後に作る操作。「複製」とは呼ばない。 |
| 並べ替え | `moveOrder` | 確定 | 注文の表示順を変える操作。計算結果には影響しない。 |
| 内訳の区分 | `PointGroup` | 確定 | 内訳を表示するときの4区分。通常（`base`）、SPU、マラソン（買いまわり）、キャンペーン（ショップ倍率を含む）の順に、どの画面でも同じ見た目で並べる。 |
| ショップ | `Shop` | 検討中 | 注文の相手となる店舗（楽天市場の各店舗、楽天ブックスなど）。楽天と同じく、1つの注文は1つのショップに属する。ショップは内部 ID で参照し、同一性はショップコードがあればショップコードで、なければユーザーが台帳から選んだかどうかで判定する。 |
| ショップコード | `shopCode` | 確定 | 楽天市場がショップに割り当てる識別子。商品 URL `https://item.rakuten.co.jp/<ショップコード>/<商品管理番号>/` やショップ URL `https://www.rakuten.co.jp/<ショップコード>/` から取り出せる。 |
| ショップ台帳 | `ShopRegistry` | 確定 | 登録済みのショップの一覧で、プランをまたいで共有する。注文でショップを指定するときは、台帳から選ぶか新しく登録する。商品 URL を貼るとショップコードで台帳のショップに紐づき、台帳になければ登録する。 |
| 商品情報の取得 | `ItemLookup` | 確定 | 商品 URL から組み立てた商品コード（`ショップコード:商品管理番号`）で楽天市場の商品検索 API を呼び、商品名、価格、ショップ名などを注文の入力に補う処理。ブラウザから直接呼ぶ。通信に失敗しても、URL からのショップコードの取り出しは通信なしで行う。 |
| 購入先 | `Channel` | 確定 | 注文が行われるサービスの区分。最初のリリースでは楽天市場、楽天ブックス、ラクマに対応する。購入先ごとに、買いまわりのショップ数に数えるかどうか、買いまわりの倍率が乗るかどうか、商品情報の取得に対応するかなどの規則が異なる。新しい購入先は拡張点に1つ追加する。 |
| ショップ数 | `ShopCount` | 確定 | 買いまわりの段階を決める数。ショップごとに期間中の税込の対象額（クーポン適用後、送料除く）を累計し、1,000円以上のショップを1と数える。同じショップで何回買っても1である。数えるかどうかは購入先の規則に従う。 |
| 対象額 | `TargetAmount` | 確定 | ポイント計算の基準になる商品ごとの金額。税込の対象額は「単価 × 数量 − 値引額」、税抜の対象額は税込の対象額から消費税額（税込額 × 税率 ÷ (1 + 税率) の切り捨て）を引いた額である。非課税の商品は税込と税抜の対象額が等しい。 |
| 端数の単位 | `roundingUnit` | 確定 | 特典のポイントの端数を切り捨てる単位。`item` は商品ごと、`order` は注文ごとに切り捨てる。多くの特典は `item` で、楽天カードの SPU などが `order` である。 |

## 計算結果

| 用語 | 英語名 | 状態 | 定義 |
|---|---|---|---|
| 内訳 | `Breakdown` | 確定 | 計算結果を「商品 × 特典」ごとのポイントで表したもの。合計はこの内訳の和として求める。 |
| 按分 | `Allocation` | 確定 | 注文単位や特典単位で求めたポイントを、商品ごとの内訳へ割り振る処理。最大剰余法で行い、割り振った値の和を元の値と一致させる。上限で削った後のポイントも按分して内訳に反映する。 |

## 保存

保存データは端末内（IndexedDB）に置き、消えてもよいものとして扱う。消えないことが求められる保存は、将来の D1 保存で提供する。

| 用語 | 英語名 | 状態 | 定義 |
|---|---|---|---|
| リポジトリ | `Repository` | 確定 | プラン、プロフィール、ショップ台帳を読み書きする非同期のインターフェース。保存先の違いを隠す層であり、いまは IndexedDB の実装（Seitu を使う）だけを持つ。将来は D1 の実装を加え、ログインした利用者は D1、ログインしない利用者は IndexedDB を使う。画面からは TanStack Query を通してだけ呼ぶ。 |
| マスタデータ | `MasterData` | 確定 | 公式イベントと SPU の標準定義。リポジトリ（Git）内のデータファイルとして書き、ビルド時に Valibot で検証して静的に配信する。更新はプルリクエストのマージとデプロイで行う。 |
| スキーマバージョン | `SchemaVersion` | 確定 | 端末に保存するデータの形式の版番号。レコードごとではなく、IndexedDB のデータベースの版として全体で1つだけ持つ。 |
| マイグレーション | `Migration` | 確定 | 古いスキーマバージョンのレコードを1つ次の版の形へ変換する純粋関数。データベースを開くときに、保存されている版から最新版まで順に全レコードへ適用し、結果を Valibot で検証する。 |
| 更新日時 | `updatedAt` | 確定 | 各レコードの最終更新日時。今は使わないが、将来 D1 と同期するときに競合の判定に使うため最初から持たせる。 |
